# bot-mineflayer

A Minecraft bot that plays the game on an agent's behalf. It holds one game connection, dials
[`mcp-server`](https://github.com/mc-agents/mcp-server) over the bot protocol, and answers tool
calls with what it sees. It knows nothing about MCP; the server knows nothing about mineflayer.

This is the light bot of the two. It is a client reimplemented in JavaScript, so it cannot render
anything and cannot press a dialog button — `bot-fabric` runs a real client for that, at about six
times the memory. Anything that does not need pixels should run here.

The design both repositories follow is in
[`mcp-server/docs/architecture.md`](https://github.com/mc-agents/mcp-server/blob/main/docs/architecture.md),
and the wire contract is
[`mcp-server/docs/bot-protocol.md`](https://github.com/mc-agents/mcp-server/blob/main/docs/bot-protocol.md).

## What it does

42 of the catalogue's 44 bot tools: moving, digging, placing, crafting, smelting, fishing,
containers and GUI windows, inventory, entities, and reading the HUD — scoreboard, boss bars, tab
list, action bar, titles and dialogs. The two it does not implement are `screenshot` and
`press-dialog-button`, which are fabric's.

It pushes five event feeds — `chat`, `actionBar`, `title`, `dialog`, `effect` — rather than
waiting to be asked, and folds the repeats so a HUD redrawn twenty times a second crosses the wire
once a second.

## How the pieces sit

```
mcp-server :8765 ◀── the bot dials ── RpcClient ── Dispatcher ── 42 tools
                                          │            │
                                      EventFolder   BotHost ── mineflayer ── the game
```

| Path | What lives there |
| --- | --- |
| `src/rpc/` | framing, the link, the dispatcher, `defineTool`, the tool catalogue |
| `src/bot/` | the game connection and the protocol patches mineflayer needs |
| `src/minecraft/` | game knowledge: chat components, NBT, windows, scoreboards, dialogs |
| `src/tools/` | the tool bodies, one file per group |
| `scripts/rpc-cli.ts` | stands in for mcp-server so the bot can be driven by hand |

Four things are worth knowing before changing any of it.

**The catalogue belongs to mcp-server.** Defaults, clamping and coordinate flooring happen there,
so two bots cannot hold different opinions about what `range` means. What arrives here is already
normalised, and the zod shapes are defensive decoding rather than validation — a shape that
refuses its input means the two sides disagree about the catalogue, which is why that failure is
`args` (disables one tool) and not `tool` (blames the game).

**The argument hashes are copied, not derived.** `src/rpc/catalog-hashes.ts` is generated by
`pnpm sync:catalog` from `catalog.json`. A hash the bot computed itself would agree with nothing
but itself.

**One `result` per `call.id`, always.** A deadline, a cancel and a tool finishing all race in the
dispatcher; the first to arrive is the answer and the rest are dropped. Cancellation is
cooperative — nothing in mineflayer can be stopped mid-walk — so a cancelled call is answered at
once while the walk carries on until its own timeout.

**Only one exclusive tool at a time.** Two things moving the bot at once would fight, so the
second is refused with `BOT_BUSY` rather than queued.

## Developing

```bash
pnpm install
docker compose -f dev/compose.yml up -d   # Paper 26.1.2 on :25577, flat, creative, offline
node scripts/rpc-cli.ts                   # listens on :8765 in place of mcp-server
MCP_SERVER_HOST=127.0.0.1 pnpm dev        # in another shell
```

Then drive it:

```
connect 127.0.0.1 25577 mcp_probe
get-position
give-item {"itemName":"chest","count":1}
equip-item {"itemName":"chest"}
place-block {"x":3,"y":-60,"z":-6,"faceDirection":"down"}
open-container {"x":3,"y":-60,"z":-6}
read-window
```

The CLI does not normalise arguments the way mcp-server does, which is the point: calling a tool
with half its arguments is how the defensive decoding gets exercised. `help` lists what it
understands.

```bash
make check   # version, typecheck, lint, test
```

Library APIs get checked by running them, not by reading about them. Every workaround in
`src/minecraft/` and `src/bot/patches.ts` is there because the documented behaviour turned out to
be wrong on 26.1.

### Adding a tool

1. Add it to `catalog.json` in mcp-server and run `pnpm sync:catalog` here.
2. Write the body with `defineTool(name, description, shape, run)` in the matching `src/tools/`
   file, and export it from the array that file already has.
3. Add the name to the list in `test/catalog.test.ts`. The list is written out rather than
   counted, so a tool that stops being registered fails the build instead of going quiet.

## Configuration

The operator starts these pods, so everything is environment; there are no flags.

| Variable | Default | Meaning |
| --- | --- | --- |
| `MCP_SERVER_HOST` | `127.0.0.1` | Where mcp-server listens for bots |
| `MCP_SERVER_PORT` | `8765` | |
| `BOT_NAME` | `$POD_NAME`, else the hostname | The name the bot introduces itself by |
| `MC_VERSION` | `auto` | Protocol version to force instead of detecting one |
| `HEALTH_PORT` | `8080` | `/healthz`, `/readyz`, `/metrics` |
| `HEALTH_BIND_HOST` | `0.0.0.0` | |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `RECONNECT_MIN_MS` | `500` | First backoff after the link drops |
| `RECONNECT_MAX_MS` | `15000` | Ceiling for that backoff |

`/readyz` wants a link to mcp-server; `/healthz` does not, because a bot waiting for the server to
come back is healthy without being useful.

## Known limits

**The bot port is not authenticated.** A NetworkPolicy opens it to mcp-server and nothing else.
Per-bot tokens would hand the operator a secret rotation problem for a port that never leaves the
cluster, so that trade was taken deliberately rather than forgotten.

**Results carry text, not structured data yet.** The catalogue marks fifteen tools as
`structured`, meaning the bot should send a DTO and let the server render it, so that two bots
cannot describe the same state in two different strings. Those tools currently send the string
they have always sent. TODO before the fabric bot answers the same calls.

**Dialog buttons cannot be pressed.** `custom_click_action` is in the 26.1 protocol mappings with
no field definition, so it cannot be serialised; sending the `latest` shape makes the server drop
the connection. Dialogs are read, never answered. This is one of the reasons `bot-fabric` exists.

**A kick is not retried.** The link to mcp-server reconnects on its own, but a bot kicked out of
the game stays out until the server sends another `connect`.
